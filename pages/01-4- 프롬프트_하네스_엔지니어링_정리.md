## 1.1 프롬프트 엔지니어링의 정의

**프롬프트 엔지니어링(Prompt Engineering)** 이란 거대언어모델(LLM)로부터 원하는 결과를 얻기 위하여 입력값, 즉 프롬프트(prompt)를 설계하고 개선하는 작업을 의미한다. 이 과정에서 모델의 가중치나 구조는 변경하지 않으며, 입력 문장의 구성만으로 출력의 품질을 조정한다는 점이 특징이다. 프롬프트 엔지니어링은 원칙적으로 단일 턴(single turn), 즉 하나의 질의와 하나의 응답으로 이루어지는 상호작용 안에서 모델의 성능을 최적화하는 데 초점을 둔다.

### 1.1.1 주요 기법

아래 표는 프롬프트 엔지니어링에서 널리 사용되는 기법을 정리한 것이다.

| 기법 | 정의 | 예시 |
|---|---|---|
| 명확하고 구체적인 지시 | 모호한 표현을 지양하고 원하는 결과를 구체적으로 명시하는 방법 | "글을 써 달라" 대신 "300자 분량의 블로그 서론을 친근한 어조로 작성하라"고 지시함 |
| 역할 부여(Role Prompting) | 모델에 특정 역할이나 페르소나를 부여하여 응답의 관점과 문체를 유도하는 방법 | "당신은 10년 경력의 백엔드 개발자이다. 아래 코드를 검토하라" |
| 예시 제공(Few-shot / One-shot) | 원하는 입출력 패턴의 예시를 하나 이상 제시하는 방법 | 번역 예시 2~3개를 먼저 제시한 뒤 새로운 문장의 번역을 요청함 |
| 단계별 사고 유도(Chain-of-Thought) | 중간 추론 과정을 거치도록 유도하여 복잡한 문제의 정확도를 높이는 방법 | 수학 문제, 논리 퍼즐 등에 적용 |
| 구조화(XML 태그, 마크다운 등) | 긴 프롬프트 안에서 지시사항, 참고자료, 출력형식을 태그나 구획으로 분리하는 방법 | `<지시사항>...</지시사항>`, `<참고자료>...</참고자료>` |
| 출력 형식 지정 | JSON, 표, 글자 수 제한 등 원하는 출력 형식을 명시하는 방법 | "JSON 형식으로만 응답하고 다른 설명은 포함하지 말라" |
| 부정·긍정 예시 병기 | 하지 말아야 할 예시와 해야 할 예시를 함께 제시하여 경계를 명확히 하는 방법 | — |
| 반복과 평가(Iteration) | 결과를 확인하며 프롬프트를 점진적으로 개선해 나가는 과정 | — |

### 1.1.2 프롬프트 엔지니어링의 한계

프롬프트 엔지니어링은 모델이 한 번의 응답에서 얼마나 정확하고 유용한 결과를 산출하는가에 초점을 맞춘다. 그러나 실제 응용에서는 모델이 여러 단계에 걸쳐 도구를 호출하고, 파일을 수정하며, 스스로 실패를 감지하고 복구해야 하는 경우가 빈번하다. 이러한 다단계 자율 행동의 신뢰성은 프롬프트 설계만으로 확보하기 어려우며, 이 문제의식에서 **하네스 엔지니어링**이라는 개념이 등장하였다.

## 1.2 하네스 엔지니어링의 정의

### 1.2.1 용어의 등장 배경

'하네스 엔지니어링(Harness Engineering)'이라는 용어는 2026년 2월 HashiCorp의 창업자이자 Terraform의 공동개발자인 Mitchell Hashimoto가 자신의 블로그에서 처음 사용하였다. 그는 AI 에이전트가 오류를 일으킬 때마다 동일한 오류가 재발하지 않도록 에이전트를 둘러싼 환경, 즉 하네스에 영구적인 수정을 가하는 작업 방식을 "engineering the harness"라고 명명하였다. 이후 수 주 내에 OpenAI와 Anthropic이 이 개념을 확장한 기술 문서를 발표하면서 해당 용어가 업계 전반으로 확산되었다.

### 1.2.2 정의

**하네스(harness)** 란 추론을 담당하는 모델을 둘러싸고 실제 행동을 산출하는 실행 환경 및 인프라를 의미한다. 하네스는 다음 요소를 포함한다.

- 에이전트가 사용할 수 있는 도구(tool)의 범위
- 에이전트가 정보를 획득하는 경로(컨텍스트, 메모리, 문서)
- 에이전트가 자신의 결정을 검증하는 방식
- 작업을 중단하거나 사람의 승인을 요청해야 하는 시점
- 실패를 감지, 기록, 복구하는 절차(관측성, observability)

이를 요약하면, 모델은 사고를 담당하고 하네스는 그 사고를 실제 행동으로 전환하고 검증하는 역할을 담당한다고 할 수 있다. 사용되는 모델의 종류와 무관하게, 그 위에 어떠한 하네스가 구축되는가에 따라 실제 성능과 신뢰성에는 상당한 차이가 발생한다.

### 1.2.3 프롬프트 엔지니어링과의 비교

| 구분 | 프롬프트 엔지니어링 | 하네스 엔지니어링 |
|---|---|---|
| 대상 | 모델에 주어지는 입력 텍스트 | 모델을 둘러싼 실행 환경과 인프라 |
| 범위 | 단일 턴(하나의 질의-응답) | 여러 턴에 걸친 자율적 작업 전체 |
| 목표 | 더 나은 단일 응답의 산출 | 반복 가능하고 검증 가능하며 통제된 자율 행동의 구현 |
| 사례 | "단계별로 사고하라"와 같은 지시문 작성 | 에이전트의 산출물을 자동 테스트로 검증하고, 실패 시 재시도를 수행하는 체계의 구축 |

### 1.2.4 하네스의 구성 요소

하네스는 다음 여섯 가지 요소로 구성된다.

1. **도구 인터페이스(Tool Interface)**: 에이전트가 호출할 수 있는 함수 및 API의 목록과 권한
2. **컨텍스트·메모리 관리**: 프로젝트 파일, 이전 대화 기록, 규칙 문서(예: 에이전트가 수정 가능한 파일과 준수해야 할 규칙을 명시한 `AGENTS.md` 문서) 등을 제공하고 유지하는 방식
3. **검증 및 평가(Verification, Evals)**: 자연어로 작업 완료를 선언하는 것이 아니라, 테스트 통과나 정적 분석 통과와 같은 증거에 기반하여 완료 여부를 판단하는 절차
4. **가드레일 및 권한(Guardrails, Permissions)**: 에이전트가 수행해서는 안 되는 행동과 사람의 승인이 필요한 행동을 명시적 규칙으로 제한하는 장치
5. **관측성 및 추적(Observability, Tracing)**: 에이전트가 특정 파일을 선택한 이유, 호출한 도구, 실패 원인 등을 기록하여 사람이 확인할 수 있도록 하는 장치
6. **실패 원인 분류 후 복구(Attribution before Recovery)**: 실패 시 무조건적인 재시도 대신 원인을 먼저 분류하고 진단한 후 다음 행동을 결정하는 절차

### 1.2.5 사례 연구: Anthropic의 3-에이전트 하네스 실험

Anthropic은 장시간 실행되는 애플리케이션 개발을 위한 하네스 설계에 관한 2026년 연구에서, 2차원 레트로 게임 엔진을 제작하는 과제를 통해 단독으로 작업하는 에이전트와 세 가지 역할(Planner, Generator, Evaluator)로 구성된 하네스를 비교하였다.

- **Planner**: 단순한 요청을 전체 제품 사양으로 확장하되, 구현 세부사항은 의도적으로 남겨둔다. 이는 초기 단계에서 지나치게 구체화할 경우 이후 단계에서 오류가 연쇄적으로 발생할 수 있기 때문이다.
- **Generator**: 실제 기능을 스프린트 단위로 구현하며, 코딩을 시작하기 전에 Evaluator와 해당 스프린트의 완료 기준을 사전에 합의한다(sprint contract).
- **Evaluator**: 브라우저 자동화 도구인 Playwright를 사용하여 실제 사용자처럼 인터페이스를 조작하며 UI, API, 데이터베이스의 동작을 검증한다. 검증에 실패하면 해당 스프린트는 실패로 처리된다.

실험 결과, 단독으로 작업한 에이전트는 표면적으로는 실행 가능한 게임을 만들어냈으나 소스코드 내부에서 개체(entity)와 런타임 간의 연결이 끊어져 있는 등 코드를 직접 검토해야만 발견되는 결함을 포함하고 있었다. 반면 3-에이전트 하네스는 더 견고한 결과물을 산출하였다.

### 1.2.6 하네스 엔지니어링의 필요성

프롬프트가 정교하게 설계되었다 하더라도, 에이전트가 여러 단계에 걸쳐 도구를 사용하고 자율적으로 행동할 경우 중간 과정이 불투명해지는 문제와 실패를 성공으로 오판하는 문제가 발생할 수 있다. 하네스 엔지니어링은 모델 자체를 교체하지 않고도 에이전트를 둘러싼 체계(테스트, 권한, 추적, 메모리 구조)를 설계함으로써 이러한 문제를 해결하고자 하는 접근이다. 관련 연구에 따르면 모델을 교체하지 않고 하네스만 개선하는 것만으로도 에이전트의 성능 순위가 크게 상승하는 사례가 보고된 바 있다.

## 1.3 두 개념의 관계

```
프롬프트 엔지니어링           하네스 엔지니어링
   (입력 설계)      ⊂ 포함됨 ⊂    (실행 환경 전체 설계)

"모델에게 무엇을 지시할 것인가"  →  "모델 주변에 어떠한 도구·검증·규칙·기록 체계를 둘 것인가"
```

프롬프트 엔지니어링은 하네스를 구성하는 하나의 요소로 볼 수 있다. 즉 하네스 내부에서도 각 에이전트에게 적절한 프롬프트를 제공하는 작업은 여전히 중요하다. 단순한 대화형 챗봇 활용의 경우 프롬프트 엔지니어링만으로 충분한 경우가 많으나, 코딩 에이전트와 같이 자율적으로 여러 단계의 작업을 수행하는 시스템을 구축할 때는 하네스 엔지니어링까지 함께 고려해야 신뢰할 수 있는 결과를 확보할 수 있다.

> **참고**: 하네스 엔지니어링이라는 용어는 2026년 2월 Mitchell Hashimoto의 블로그 게시물에서 시작되어 이후 OpenAI와 Anthropic의 관련 문서를 통해 빠르게 확산된 신조어이다. 아직 학계와 업계에서 표준화가 진행 중인 개념이므로 출처에 따라 세부 정의에 차이가 있을 수 있다.

## 1.4 심화 논의: 모델 성능 향상과 프롬프트 설계의 중요도

이 절에서는 "모델의 성능이 향상됨에 따라 프롬프트 설계의 중요성이 감소하였다"는 주장을 실증 연구를 근거로 검토한다.

### 1.4.1 소결론

해당 주장은 실증 연구로 검증할 경우 일반화하기 어려운 것으로 나타난다. 다만 특정 유형의 표면적 기법이 효력을 상실한 것은 사실이며, 이를 근거로 프롬프트 엔지니어링 자체가 불필요해졌다고 확대 해석하는 것은 타당하지 않다.

### 1.4.2 주장을 뒷받침하는 근거

| 내용 | 근거 |
|---|---|
| 특정 유도 문구(예: 사고연쇄 유도어)는 RLHF(인간 피드백 강화학습) 훈련 과정에 흡수되어 추가적인 효과를 상실하였다 | 최신 모델이 인터넷상의 프롬프트 관련 게시물을 학습 데이터 및 보상 모델에 흡수함에 따라 해당 기법이 모델의 기본 동작으로 편입되었다는 관찰 |
| 지시 튜닝(instruction-tuning)이 이루어진 대형 모델일수록 프롬프트 템플릿 변화에 대한 결과 편차가 더 작다 | 중국어 LLM 평가 플랫폼 CLEVA의 연구 — 소형 모델(ChatGLM2-6B, Baichuan-7B)이 대형 모델보다 표준편차가 더 크다는 결과 |
| 대형 LLM일수록 프롬프트 변형에 상대적으로 더 견고하며, 퓨샷 예시 제공이 견고성을 향상시킨다 | PromptSensiScore(ProSA) 연구 |

### 1.4.3 주장을 반박하는 근거

| 내용 | 근거 |
|---|---|
| 모델의 성능과 프롬프트 민감도 사이에는 뚜렷한 상관관계가 확인되지 않으며, 성능이 뛰어난 모델이 반드시 더 안정적인 응답을 산출하는 것은 아니다 | 코드 생성 벤치마크 8종과 오픈소스 LLM 10종을 대상으로 한 대규모 실험 |
| 최상위권 모델도 최악의 조건에 해당하는 프롬프트에서는 예측하기 어려운 성능 저하를 나타낸다 | RobustAlpacaEval 벤치마크(Llama, Mistral, Gemma 계열 모델 대상) |
| 성능이 우수한 모델도 특정 과제(예: 요약)에서는 프롬프트에 따라 상당한 편차를 보인다 | CLEVA 연구 내 예외 사례(GPT-4) |

### 1.4.4 핵심 논점: 중요성의 소멸이 아닌 층위의 이동

무력화된 것은 벤치마크 점수 향상을 목적으로 발견된 표면적 기법(특정 사고연쇄 유도어, 특정 페르소나 서두, 탈옥형 문구 등)이며, 명확한 지시, 적절한 예시 제공, 컨텍스트 구조화와 같은 근본 원칙이 무력화된 것은 아니다.

2026년의 한 컨텍스트 관리 현황 보고서에 따르면 IT 및 데이터 부문 책임자의 82퍼센트가 "프롬프트 엔지니어링만으로는 AI를 대규모로 운영하기에 충분하지 않다"는 데 동의하였다. 이는 프롬프트가 불필요하다는 의미가 아니라, 프롬프트 설계만으로는 부족하며 컨텍스트, 스키마, 검증 체계를 함께 설계해야 한다는 의미로 해석하는 것이 타당하다. 이러한 흐름은 앞서 논의한 하네스 엔지니어링의 등장 배경과도 맥락을 같이한다.

### 1.4.5 효력을 상실한 표면적 기법의 유형

**(1) 사고 유도 문구(Reasoning Trigger Phrases)**

"단계별로 생각해보라(Let's think step by step)"는 2022년의 연구에서 처음 제시된 제로샷 사고연쇄 유도 기법으로, 초기 모델에서 산술 및 논리 문제의 정확도를 크게 향상시켰다. "심호흡을 하고 단계별로 생각해보라"는 표현은 초기 모델에서 초등 수준 수학 문제의 정확도를 약 7퍼센트포인트 향상시켰다는 보고가 있었으나, 이후 해당 표현에 대해 RLHF가 적용된 모델에서는 그 효과가 거의 사라진 것으로 나타났다. 최신 추론 특화 모델은 별도의 유도 문구 없이도 내부적으로 단계별 추론을 수행하도록 훈련되어 있어 유사한 효과를 얻을 수 있다.

**(2) 페르소나 및 역할 부여형 서두**

"당신은 세계 최고 수준의 전문가이다", "당신은 10년 경력의 시니어 개발자이다"와 같은 역할 부여형 서두 문구는 이후 훈련 과정 및 모델 앞단의 별도 분류기(constitution classifier 등)에 흡수되면서 차별화된 효과가 감소하였다.

**(3) 감정적 또는 동기 부여형 호소 문구**

"이 작업은 나의 경력에 매우 중요하다", "정답을 맞히면 보상을 지급하겠다"와 같은 감정적 호소나 보상 약속 문구는 초기에는 미세한 성능 향상이 보고되기도 하였으나, 모델이 이러한 문구와 무관하게 최선의 결과를 산출하도록 훈련됨에 따라 그 효과가 감소하였다.

**(4) 탈옥형(Jailbreak) 문구**

"DAN(Do Anything Now)"이나 "이전 지시를 무시하라"와 같은 프롬프트 삽입형 문구는 안전성 관련 파인튜닝 및 별도 분류기 단계에서 광범위하게 학습 및 대응됨에 따라 이전만큼의 효력을 상실하였다.

**(5) 자연어를 통한 출력 형식 강제 문구**

"반드시 JSON 형식으로만 응답하고 다른 설명은 포함하지 말라"와 같은 형식 강제 문구는 그 자체가 무력화되었다기보다는, 프로바이더가 제공하는 구조화 출력 기능(OpenAI의 JSON 모드 및 함수 호출, Anthropic의 도구 사용 스키마, Gemini의 제어된 생성 등)으로 대체되었다고 보는 것이 정확하다.

### 1.4.6 효력 상실의 메커니즘

효력을 상실한 기법들은 다음 두 가지 메커니즘 중 하나로 설명할 수 있다.

1. **흡수(Absorption)**: 특정 기법이 널리 알려지면서 학습 데이터 및 RLHF 보상 신호에 포함되었고, 모델이 해당 기법 없이도 동일한 행동을 기본값으로 수행하도록 학습된 경우이다. 사고 유도 문구, 페르소나 서두, 탈옥형 문구가 이에 해당한다.
2. **대체(Substitution)**: 프롬프트를 통해 우회적으로 달성하던 목적을 시스템 차원의 정식 기능이 대신하게 된 경우이다. 자연어를 통한 형식 강제가 구조화 출력 스키마로 대체된 사례가 이에 해당한다.

이러한 논의는 무작위적으로 발견된 표면적 기법에 한정되며, 명확한 지시, 적절한 예시 제공, 컨텍스트 구조화와 같은 근본적인 프롬프트 설계 원칙 자체는 여전히 유효하다는 점에 유의할 필요가 있다.

## 요약

- 프롬프트 엔지니어링은 모델에 대한 입력 설계를 통해 단일 턴의 응답 품질을 최적화하는 작업이다.
- 하네스 엔지니어링은 모델을 둘러싼 실행 환경 전반을 설계하여 여러 턴에 걸친 자율적 작업의 신뢰성을 확보하는 작업이며, 2026년에 등장한 개념이다.
- 두 개념은 대립하는 것이 아니라 포함 관계에 있으며, 작업의 복잡도에 따라 요구되는 설계 범위가 달라진다.
- 모델 성능 향상이 프롬프트 설계의 중요성을 전반적으로 감소시켰다는 주장은 실증 근거로 일반화하기 어려우며, 특정 표면적 기법의 효력 상실과 근본적 설계 원칙의 지속적 유효성을 구분하여 이해해야 한다.
