# 웹지도 제작과 배포의 개념과 이론

# 제1부. 기본 이론

## 1. 웹지도의 원리

### 1.1 정적 지도와 웹지도의 차이

QGIS와 같은 데스크톱 GIS 소프트웨어에서 제작한 지도는 해당 소프트웨어가 설치된 컴퓨터에서만 열람할 수 있다. 반면 웹지도(Web Map)는 브라우저만 있으면 별도의 소프트웨어 설치 없이 누구나 열람할 수 있는 지도를 말한다. 이 차이는 지도를 하나의 완성된 이미지로 다루는지, 아니면 여러 층(layer)을 브라우저가 실시간으로 합성하는지의 차이에서 비롯된다.

### 1.2 타일과 GeoJSON

- **배경 타일(Tile)**: 웹지도의 배경(도로, 지형, 건물 등)은 일정한 크기로 잘게 분할된 이미지 조각(타일)을 확대·축소 수준(zoom level)에 맞추어 불러와 이어 붙이는 방식으로 표시된다. OpenStreetMap과 같은 서비스가 이러한 타일을 무료로 제공한다.
- **GeoJSON**: 점·선·면과 같은 지리 데이터를 JSON(JavaScript Object Notation) 형식으로 표현한 개방형 표준 포맷이다(Butler et al., 2016). 웹 브라우저가 별도의 변환 없이 곧바로 읽어 표시할 수 있어, 웹지도에서 사용자 데이터를 표현하는 표준적인 방법으로 활용된다.

### 1.3 좌표계 (EPSG:4326과 EPSG:3857)

데스크톱 GIS 분석에서는 거리·면적 계산의 정확도를 위해 투영좌표계(예: EPSG:5179)를 사용하는 경우가 많다. 이러한 데이터를 웹지도에서 사용하려면 좌표계를 다시 맞추어야 하는데, 이때 역할이 서로 다른 두 좌표계를 구분할 필요가 있다.

- **GeoJSON 데이터, 라이브러리에 입력하는 위경도 값**: GeoJSON 표준(RFC 7946)은 좌표계를 위경도 좌표계인 **EPSG:4326(WGS84)**으로 고정하며, 그 외의 좌표계는 표준에서 허용하지 않는다(Butler et al., 2016). Leaflet과 같은 라이브러리에 위치를 전달할 때도 이 위경도(EPSG:4326) 값을 사용한다.
- **배경 타일, 지도 렌더링(투영)**: OpenStreetMap 등 대부분의 배경 타일 서비스와 Leaflet의 실제 지도 표시(투영)는 **EPSG:3857(Web Mercator)**을 사용한다. 즉 지도가 화면에 그려지는 방식 자체는 EPSG:4326이 아니라 EPSG:3857을 따른다.

두 좌표계 사이의 변환은 라이브러리가 자동으로 처리하므로, 제작자가 직접 신경 써야 하는 부분은 **GeoJSON을 만들 때 EPSG:4326으로 맞추는 것**이다. 따라서 투영좌표계로 제작된 데이터를 웹지도에 사용하려면, GeoJSON으로 내보내는 단계에서 EPSG:4326으로 재투영하는 과정이 필요하다.

## 2. 웹지도 제작 방식

### 2.1 자동 변환 도구

QGIS2Web과 같은 플러그인은 QGIS에서 제작한 레이어를 별도의 코드 작성 없이 Leaflet 기반 웹지도로 자동 변환한다. 레이어 스타일(심볼로지)이 자동으로 반영되며, 짧은 시간에 결과물을 얻을 수 있다는 장점이 있으나, 세부 기능(필터, 애니메이션 등)을 추가하려면 도구가 제공하는 옵션 범위 안에서만 조정이 가능하다.

### 2.2 코드 기반 제작 (Leaflet)

Leaflet은 웹지도를 제작하기 위한 대표적인 오픈소스 자바스크립트 라이브러리이다. 배경 타일과 GeoJSON 데이터를 코드로 직접 결합하여 지도를 구성하며, 마커 색상, 팝업 내용, 범례, 필터 등을 원하는 대로 세밀하게 구현할 수 있다는 장점이 있다. 다만 코드를 직접 작성(또는 AI에게 요청)해야 하므로, 자동 변환 도구보다 초기 제작 시간이 더 소요될 수 있다.

### 2.3 두 방식의 비교 관점

두 방식은 상호 배타적이지 않으며, 목적에 따라 선택하거나 병행할 수 있다. 일반적으로 비교되는 항목은 다음과 같다: 제작 소요 시간, 스타일·색상 표현의 자유도, 범례·팝업 등 부가 요소의 자동화 여부, 제작자가 결과 코드를 이해하고 있는 정도, 다른 프로젝트로의 재사용 가능성.

## 3. AI를 활용한 코드 생성과 수정

### 3.1 신규 코드 생성 요청 시 고려사항

AI에게 처음부터 코드를 요청할 때는 다음 요소를 프롬프트에 명시하는 것이 결과물의 품질에 영향을 준다.

- **역할**: AI가 수행할 전문 분야를 지정한다 (예: "Leaflet 전문 프론트엔드 개발자").
- **맥락**: 입력 데이터의 출처, 구조, 필드의 의미를 설명한다.
- **요청**: 구현해야 할 기능을 동작 단위로 구체적으로 나열한다.
- **제약**: 결과물의 형태(파일 구성, 라이브러리 로딩 방식 등)를 지정한다.
- **검증**: 완성된 결과가 요청 사항을 실제로 충족하는지 AI 스스로 대조하도록 요청한다.

### 3.2 부분 수정 요청 시 유의사항

이미 작성된 코드에 기능을 추가하거나 수정할 때, "고쳐줘"와 같이 요청 범위를 명시하지 않으면 AI가 기존 코드를 참고만 하고 전체를 새로 작성하는 경우가 있다. 이 경우 다음과 같은 문제가 발생할 수 있다.

- 이미 검증된 코드가 다시 불안정해진다.
- 이전에 이해한 코드 구조가 초기화된다.
- 수정 전후 비교가 어려워진다.

이를 방지하기 위해 프롬프트에 "기존 코드 구조는 유지"와 같은 유지 조건(제약)을 명시하고, 기존 코드 전체를 맥락으로 함께 제공하는 것이 권장된다.

## 4. 인터랙티브 UI와 이벤트 처리

### 4.1 인터랙티브 UI

인터랙티브 UI(Interactive User Interface)는 사용자가 필터, 검색, 슬라이더 등을 조작하여 원하는 데이터만 탐색할 수 있도록 지원하는 인터페이스를 말한다. 정적인 지도가 모든 정보를 한 번에 보여주는 것과 달리, 인터랙티브 UI는 사용자가 조건을 바꾸어가며 필요한 정보만 선택적으로 확인할 수 있게 한다.

### 4.2 이벤트 처리

이벤트 처리(Event Handling)는 "사용자의 특정 조작(클릭, 슬라이더 이동 등)이 발생했을 때, 특정 동작을 실행하도록 연결하는 것"을 말한다. 웹 프로그래밍에서는 일반적으로 `addEventListener`와 같은 함수를 이용해 이벤트와 처리 동작을 연결한다.

## 5. 정적 사이트 배포 (GitHub Pages)

### 5.1 정의

GitHub Pages는 GitHub 저장소에 저장된 정적 파일(HTML, CSS, JavaScript 등)을 별도의 서버 구축 없이 인터넷에 공개할 수 있도록 지원하는 무료 호스팅 서비스이다. 저장소 안에 `index.html` 파일을 두고 배포 설정을 활성화하면, 고유한 인터넷 주소가 발급된다.

### 5.2 공개 저장소와 데이터 보안

GitHub Pages를 무료로 사용하려면 저장소를 공개(Public)로 설정해야 하며, 이 경우 저장소에 포함된 모든 파일이 누구에게나 열람 가능한 상태가 된다. 따라서 배포 전 다음 사항을 확인해야 한다.

- 원본 데이터(민감한 위치·시설 정보 등)를 정제하지 않은 형태로 게시하지 않는다.
- API 키와 같은 인증 정보가 코드에 직접 노출되어 있지 않은지 확인한다. 노출된 경우 환경변수 분리(`.env` 파일 및 `.gitignore` 설정) 등을 통해 코드에서 분리해야 한다.

## 6. 반응형 디자인과 사용성 테스트

### 6.1 반응형 디자인(Responsive Design)

반응형 디자인은 하나의 웹페이지가 데스크톱, 태블릿, 스마트폰 등 다양한 화면 크기에서도 레이아웃이 깨지지 않고 적절히 표시되도록 설계하는 방식을 말한다(Marcotte, 2011). 웹지도의 경우 지도 영역, 슬라이더·버튼과 같은 UI 요소가 작은 화면에서도 잘리거나 겹치지 않는지 확인이 필요하다.

### 6.2 사용성 테스트(Usability Testing)

사용성 테스트는 실제 사용자(또는 잠재 사용자)에게 특정 과업을 수행하도록 요청하고, 그 과정을 관찰하여 인터페이스의 문제점을 발견하는 평가 방법이다(Nielsen, 1994). 제작자가 스스로 확인할 때는 발견하지 못하는 문제(설명 없이는 기능을 찾지 못하는 등)를 실제 사용자의 행동을 통해 확인할 수 있다는 점에서 유효하다.

# 제2부. 실습 절차

제1부에서는 웹지도 제작과 배포에 필요한 개념을 살펴보았다. 이제부터는 이 개념들을 실제 프로젝트에 적용한다.

## 프로젝트 개요

**목적**
프로젝트1(재난 대피소 입지 적합성 분석)의 결과물을 QGIS 밖에서도 누구나 열람할 수 있는 웹지도로 제작하고, 나아가 사용자가 직접 조작할 수 있는 필터를 추가한 뒤 실제 인터넷에 배포한다. 이는 "분석 결과를 어떻게 하면 QGIS가 없는 사람에게도 효과적으로 전달할 수 있는가"라는 질문에서 출발한다.

**사용 데이터**
- 프로젝트1에서 산출한 노원구 대피소 입지 적합성 분석 결과(격자 또는 대표점 단위 `suitability` 필드)
- 노원구 행정경계, 기존 대피소 위치(팝업 표시용)

**분석 구성**
동일한 데이터를 QGIS2Web과 AI 직접 코딩(Leaflet) 두 가지 방식으로 각각 웹지도로 제작하여 비교한 뒤, 한 가지 결과물에 인터랙티브 필터를 추가하고 GitHub Pages로 배포하여 실제 사용자를 대상으로 사용성을 검증한다.

**적용 방법론**
1. 웹지도 원리 이해 — 타일, GeoJSON, EPSG:4326
2. 자동 변환 — QGIS2Web을 이용한 1차 웹지도 제작
3. 코드 기반 제작 — AI를 활용한 Leaflet 직접 코딩
4. 인터랙션 구현 — 필터 슬라이더 추가 (부분 수정 요청)
5. 배포 — GitHub Pages를 통한 인터넷 공개
6. 검증 — 반응형 확인 및 사용성 테스트

**한계**
웹지도 자체는 이미 계산된 결과값을 시각화하는 것으로, 원본 분석(프로젝트1)에서 발견된 한계(예: 건축이 불가능한 지역의 과대평가)를 웹지도 단계에서 해소하지는 못한다. 따라서 웹지도에서도 동일한 한계가 재현될 수 있으며, 이는 결과와 함께 명시하는 것을 원칙으로 한다.

---

앞서 살펴본 웹지도 원리·제작 방식·AI 코드 요청·인터랙션·배포·사용성 검증 절차를 실행 순서로 재구성한 표를 아래에 제시하며, 각 단계에서 어떤 근거로 어떤 값을 결정했는지 "결정사항" 칸에 직접 기록해 나간다.

## 1. 웹지도 제작 실행 절차 (제1부 1~3절 관련)

| 순서 | 실행 내용 | 확인·결정할 사항 | 결정사항 (기입) |
|---|---|---|---|
| 1 | 웹지도 제작 대상 결정 | 어떤 프로젝트 결과물을 웹지도로 만들 것인지, 데이터 형태(포인트/폴리곤) | |
| 2 | 웹지도 표현 방식 결정 | QGIS2Web(자동 변환) vs AI 직접 코딩(Leaflet) 중 무엇을 먼저 시도할지 | |
| 3 | 팝업·색상 표현 필드 결정 | 웹지도에 표시할 핵심 필드 | |
| 4 | 좌표계 확인 | 웹지도는 EPSG:4326을 사용해야 함 — 현재 데이터 좌표계 확인 필요 | |
| 5 | AI 요청 프롬프트 구성 | 역할·맥락·요청·제약을 어떻게 구체화할지 | |
| 6 | 결과 비교 방식 결정 | 두 결과물을 어떤 기준으로 비교할지 | |

> 노원구 웹지도 제작 사례로 위 표의 "결정사항" 칸을 채운 예시는 프로젝트3 실습 절차 예시 문서(1절)에서 확인할 수 있다.

## 2. 인터랙션 구현 및 배포 실행 절차 (제1부 4~6절 관련)

| 순서 | 실행 내용 | 확인·결정할 사항 | 결정사항 (기입) |
|---|---|---|---|
| 1 | 추가할 인터랙션 기능 결정 | 어떤 필터·검색 기능이 유용할지 | |
| 2 | 수정 요청 방식 결정 | 전체 재작성 요청 vs 부분 수정 요청 | |
| 3 | 배포 플랫폼 결정 | GitHub Pages vs 기타 정적 호스팅 | |
| 4 | 업로드 파일 범위 결정 | 웹지도 HTML만 게시할지, 원본 데이터도 함께 게시할지 | |
| 5 | 반응형·사용성 검증 방법 결정 | 어떤 기기로, 어떤 과업으로 테스트할지 | |

> 노원구 웹지도 배포 사례로 위 표의 "결정사항" 칸을 채운 예시는 프로젝트3 실습 절차 예시 문서(2절)에서 확인할 수 있다.

민감도 분석(프로젝트1)과 마찬가지로, 이 프로젝트에서도 필터 기준값(2절 1번 항목)을 다르게 설정했을 때 화면에 남는 후보지가 어떻게 달라지는지 비교하는 절차가 함께 요구된다.
