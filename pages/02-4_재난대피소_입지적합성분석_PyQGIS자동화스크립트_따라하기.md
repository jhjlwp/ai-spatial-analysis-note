# 재난 대피소 입지 적합성 분석 (PyQGIS 자동화 스크립트 작성)
### (서울 노원구 시범 지역)

## 과제 제시문 (실습 시나리오)

**학습자는 서울 노원구의 재난 대피소 입지 적합성 분석 프로젝트에 참여한 팀원이다.** 전차시까지 QGIS를 손으로 조작하며 인구밀집도·기존 대피소와의 거리·도로 접근성, 세 기준으로 노원구 전역의 입지 적합도를 계산하였다.

이번 시간의 과제는 다음과 같다: **격자 생성부터 정규화·가중합, 그리고 발표 자료에 바로 쓸 수 있는 완성된 지도 출력까지, 전체 과정을 PyQGIS 스크립트 하나로 자동 재현**하는 것이다. 스크립트는 AI의 도움을 받아 작성하되, 처음부터 한 번에 완벽하게 동작하지 않는 것이 정상이다. 그 과정에서 마주치는 에러와 이상한 결과를 스스로 진단하고 해결해 나가는 것 자체가 이번 과제의 핵심이다.

**과제 완료 조건**
- 스크립트 실행 한 번으로 격자 생성 → 점수화 → 정규화·가중합 → 최종 적합도 지도 이미지 출력까지 재현된다
- 스크립트 안에 어떤 값이 고정되어 있고, 그 근거가 무엇인지 설명할 수 있다
- 자동 생성된 결과(수치·지도)를 직접 검토하여 이상 여부를 확인한다

> 각 교시는 답을 먼저 제시하지 않고, 미션 → (필요한 경우) 힌트 → 정리의 순서로 스스로 발견하도록 구성되어 있다. 막히는 지점이 있더라도 곧바로 힌트를 확인하지 말고, 먼저 스스로 고민하는 시간을 갖는다.

> ⚠️ **이 문서는 하나의 예시이다.** 실제 레이어 이름, 필드명, 스크립트의 구체적인 문법은 학습자의 QGIS 버전과 데이터에 따라 다를 수 있다. 아래 코드에 등장하는 레이어 이름·필드명(`노원구(행정경계)`, `POP_2024` 등)은 예시이므로, 2교시에서 직접 확인한 실제 이름으로 반드시 바꾸어 사용한다. 진행 중 에러가 나거나 화면이 본문과 다르게 나타난다면 멈추지 말고 AI에게 에러 메시지를 그대로 제시하며 구체적으로 질문한다.

> 📌 **이 문서의 내용은 두 종류로 나뉜다.** 아래 두 표시를 힌트·정리 블록마다 표기해 두었으므로, 어디까지가 일반적으로 성립하는 내용이고 어디부터가 "이번 예시에서 그렇게 나타났다"는 사례인지 구분하여 읽는다.
> - 🔵 **일반 원리** — 스크립트의 구체적인 형태와 무관하게 대체로 성립하는 내용 (예: 격자 간격은 도구가 자동으로 정해주지 않는다, 500m에 법적 근거가 없다는 사실 등)
> - 🟡 **이 예시 스크립트에 국한된 사례** — 이번 예시에서 AI가 실제로 작성한 특정 스크립트의 구조나 그 결과로 나타난 특정 현상 (예: 레이어를 이름으로 찾는 방식으로 구성되어 있었다는 것, 노원구 데이터에서 산지가 상위권에 포함되었다는 것). 다른 스크립트나 다른 지역 데이터에서는 다르게 나타나거나 아예 발생하지 않을 수 있다.

## 0교시 — PyQGIS란 무엇인가 (10분)

지금까지는 QGIS 화면에서 메뉴를 클릭하고 도구를 찾아 값을 입력하는 방식으로 작업하였다. 오늘부터는 이러한 작업을 **코드로 대신 실행**한다. 이때 사용하는 것이 **PyQGIS**이다.

### PyQGIS란

PyQGIS는 QGIS 내부의 기능들을 파이썬 코드로 그대로 불러와 사용할 수 있게 해주는 QGIS의 파이썬 API(인터페이스)이다. 새로운 프로그램이 아니라, **현재 사용 중인 QGIS 자체를 코드로 조작하는 방법**으로 이해하면 된다. "개발자용 도구"라기보다, 이전 차시에 마우스로 반복하였던 클릭 동작들을 한 번에 묶어 실행하는 수단에 가깝다.

### PyQGIS는 QGIS 실행 상태를 전제로 하는가

오늘 다루는 세 가지 실행 방식(Python Console, Processing Toolbox 도구, 플러그인)은 모두 **QGIS 프로그램이 실행 중이고 프로젝트가 열려 있는 상태**를 전제로 한다. 3교시에서 다루는 "레이어를 이름으로 찾는" 방식 역시 QGIS가 실행 중이어야만 의미를 갖는다 — `QgsProject.instance()`가 가리키는 대상이 바로 현재 화면에 열려 있는 그 프로젝트이기 때문이다. 이번 실습은 이러한 전제 위에서 진행된다.

> 🔵 참고로 PyQGIS API 자체는 QGIS 프로그램 창을 열지 않고도 독립적인 파이썬 스크립트로 실행하는 방법(`QgsApplication`을 직접 초기화하는 방식)이 존재한다. 서버에서 지도를 정기적으로 자동 생성하거나 GUI 없이 배치 작업을 수행할 때 사용하는 방식으로, 이번 실습의 범위를 넘어서는 심화 내용이다.

### 오늘 사용하는 세 가지 개념

프로그래밍 경험이 없더라도, 아래 세 가지 개념만 이해하면 오늘의 스크립트를 읽고 파악하는 데 충분하다.

| 개념 | 무엇인가 | 이전 차시의 작업과 비교하면 |
|---|---|---|
| **QGIS Python Console** | 코드를 입력하고 즉시 실행할 수 있는 창. `Plugins → Python Console`로 연다. | QGIS 메뉴를 하나씩 클릭하는 대신, 코드 한 덩어리를 붙여넣고 한 번에 실행하는 곳이다 |
| **`processing.run(...)`** | Processing Toolbox에 있는 도구(예: `native:creategrid`, `native:joinbynearest`)를 코드에서 그대로 호출하는 함수 | 이전 차시에 Processing Toolbox에서 검색하여 실행 버튼을 눌렀던 도구를, 코드 한 줄로 실행하는 것과 같다 |
| **`QgsProject.instance()`** | 현재 QGIS 화면에 열려 있는 프로젝트(그리고 그 안의 레이어들)에 접근하는 통로 | 왼쪽 레이어 패널에 표시된 레이어들을 코드에서 "이름으로" 찾아 사용하는 방법이다 |

### 코드를 모두 이해하지 않아도 되는 이유

오늘 학습자는 스크립트를 처음부터 직접 작성하지 않는다. AI에게 요청하여 받고, 실행하고, 결과를 검토하는 역할을 수행한다. 다만 코드를 한 줄씩 완벽히 이해할 필요는 없더라도, **코드의 각 부분이 이전 차시에 손으로 수행하였던 어떤 동작에 대응하는지** 정도는 파악해야 한다 — 그래야 에러가 발생하였을 때 어느 단계에서 문제가 생겼는지를 스스로 짚어낼 수 있기 때문이다. 아래 표로 미리 연결해 두면 3~4교시 진행이 한결 수월하다.

| 오늘 코드에서 보게 될 것 | 전차시에 손으로 수행한 작업 |
|---|---|
| `processing.run("native:creategrid", ...)` | Processing Toolbox → 격자 만들기(Create Grid) |
| `processing.run("native:joinbynearest", ...)` | 최근접 지점 결합(Join by Nearest) |
| 필드값 계산 관련 코드 | 필드 계산기(Field Calculator) |
| `QgsProject.instance().mapLayersByName("레이어 이름")` | 왼쪽 레이어 패널에서 레이어를 클릭하여 선택하는 것 |

## 오늘의 목표

전차시에서는 QGIS 메뉴를 하나하나 실행하며 격자 생성 → 인구밀도 조인 → 최근접거리 계산 → 정규화·가중합까지의 과정을 손으로 직접 진행하였다. 이번 차시가 끝나면 다음 다섯 가지가 가능해야 한다.

① 전체 과정을 버튼 한 번으로 재현하는 PyQGIS 스크립트를 보유한다.
② 스크립트가 처음에 실패하는 이유를 직접 경험하고 그 원인을 스스로 찾아낼 수 있다.
③ 스크립트 안에 어떤 임의의 선택이 숫자로 고정되어 있는지 코드를 읽고 찾아낼 수 있다.
④ 계산 결과뿐 아니라 **인쇄조판(Print Layout) 기능까지 코드로 자동화하여**, 발표에 바로 사용할 수 있는 완성된 지도 이미지를 스크립트 실행만으로 얻을 수 있다.
⑤ 완성된 스크립트를 **Processing Toolbox의 사용자 도구로 등록**하여, 매번 코드를 붙여넣지 않고도 메뉴에서 바로 실행할 수 있다.

## 오늘의 전체 흐름 (미리 보기)

이번 차시에서는 아래 흐름을 여러 차례 반복하게 된다. 처음 요청한 스크립트가 한 번에 완성되어 실행되는 경우는 드물다 — 이는 실패가 아니라 본래 이러한 방식으로 진행되는 작업이다.

```
① AI에게 스크립트 요청
   (1~2교시에서 확인한 실제 좌표계·필드명·레이어 이름을 함께 전달)
        ↓
② QGIS Python Console에서 실행
        ↓
③ 에러가 나거나, 실행은 되지만 결과가 이상함
        ↓
④ 에러 메시지 또는 이상한 결과를 AI에게 그대로 보여주며 재요청
        ↓
   (②~④를 결과가 말이 될 때까지 반복)
        ↓
⑤ 정상 실행된 결과를 지도로 직접 눈으로 확인
        ↓
⑥ 인쇄조판(Print Layout) 자동 구성 및 지도 이미지 출력
        ↓
⑦ 완성된 스크립트를 Processing Toolbox 도구로 등록
```

3~7교시는 각각 이 흐름 중 한 지점(②의 에러, ①의 숨은 선택, ⑤의 검토, ⑥의 지도 출력, ⑦의 도구 등록)에서 실제로 발생하는 일을 다룬다.

## 1교시 — 스크립트를 실행하기 전에: 이전 차시 습관 되짚기 (10분)

AI에게 스크립트를 요청하기에 앞서, 전차시에서 강조한 습관을 다시 실행한다. 이 단계를 생략하고 곧바로 스크립트를 요청하면, 이번 시간의 대부분을 오류 디버깅에 소모하게 될 가능성이 높다.

**미션:** QGIS에 세 레이어(행정동 경계+인구, 대피소, 도로중심선)를 불러온 상태에서, 각 레이어를 우클릭 → 속성(Properties) → 정보(Information) 탭을 열어 아래 사항을 확인하고 기록한다.

- [ ] 행정동 경계(+인구) 레이어 — 좌표계(EPSG 코드)는 무엇인가
- [ ] 대피소 레이어 — 좌표계는 무엇인가
- [ ] 도로중심선 레이어 — 좌표계는 무엇인가

셋 중 하나라도 다르다면 어떻게 해야 하는지, 전차시 도입부에서 다룬 내용을 떠올려 본다.

> **힌트**
> 좌표계가 다르다고 하여 지도에서 반드시 어긋나 보이는 것은 아니지만(전차시 참고), 스크립트로 거리·면적을 계산할 때는 사정이 다르다. 셋 중 하나라도 다르다면, 레이어 우클릭 → Export → Save Features As로 통일된 좌표계(예: EPSG:5179)로 미리 변환해 두는 것을 권장한다. 스크립트 실행 도중에 좌표계 문제를 처리하는 것보다, 미리 통일해 두는 편이 훨씬 간단하다.

## 2교시 — AI에게 요청하기 전에: 실제 필드명 확인 (15분)

AI에게 "인구밀도를 계산하여 격자에 조인해 달라"고만 요청하면, AI는 학습자 데이터의 실제 필드명을 알지 못한다. 짐작으로 필드명을 채운 스크립트는 대부분 실행 단계에서 에러가 발생한다.

**미션:** 각 레이어의 **속성 테이블(Attribute Table)**을 열어 아래 항목을 정확히 기록한다.

- [ ] 행정동 레이어에서 인구 관련 필드명이 정확히 무엇인가 (예시가 아니라 화면에 보이는 그대로)
- [ ] 대피소 레이어에 위도/경도 필드가 별도로 있는가, 아니면 이미 포인트 geometry로만 되어 있어 필드가 필요 없는 상태인가
- [ ] 세 레이어의 **QGIS 왼쪽 패널에 표시되는 레이어 이름**은 각각 무엇인가

**미션 2:** 위 세 가지를 확인하였다면, AI에게 스크립트를 요청할 때 이 실제 이름들을 그대로 전달한다. "인구 필드", "대피소 레이어"와 같은 일반적인 표현 대신 확인한 정확한 이름을 사용하여 요청하는 경우와 그렇지 않은 경우, 어느 쪽이 곧바로 실행되는 스크립트를 받을 가능성이 높은지 판단한다.

> **정리**
> AI는 학습자의 화면을 볼 수 없다. 필드명과 레이어 이름을 정확히 제공할수록 첫 실행에서 바로 동작하는 스크립트를 받을 확률이 높아진다. 반대로 확인 없이 요청하면 AI는 `POP_2024`, `TOT_POP`과 같은 흔한 이름을 추측하여 채울 수밖에 없으며, 그 추측이 실제 데이터와 다를 경우 스크립트는 필드를 찾지 못하고 에러를 발생시킨다.

## 3교시 — 첫 실행, 그리고 첫 번째 에러

AI에게 요청하여 스크립트를 하나 받았다고 가정한다. 이제 QGIS의 **Plugins → Python Console**을 열고 실행할 차례이다.

**미션:** 스크립트를 실행하기 **전에** 먼저 결과를 예상한다 — 현재 QGIS 왼쪽 패널에 아직 아무 레이어도 추가하지 않은 상태(또는 일부만 추가한 상태)에서 이 스크립트를 실행하면 어떤 일이 벌어질지 예상한 뒤, 실제로 실행하여 확인한다.

에러가 발생하였다면(예: 레이어를 찾을 수 없다는 메시지), 그 에러 메시지를 읽는다. **이러한 에러가 발생한 이유는 무엇인가?**

> **힌트 1 (먼저 이것만)**
> 스크립트 안에서 데이터를 가져오는 부분을 다시 확인한다. 파일 경로(`.shp` 파일이 저장된 폴더 위치)가 적혀 있는지, 아니면 레이어의 "이름"이 적혀 있는지 살펴본다.

> **힌트 2 (그래도 막히면)**
> QGIS Python Console에서 실행하는 스크립트가 데이터를 가져오는 방식은 크게 두 가지로 나뉜다 — ① 디스크의 파일을 직접 열어 읽는 방식, ② 이미 QGIS 프로젝트에 열려 있는 레이어를 이름으로 찾아 가져오는 방식. 오늘의 스크립트가 어느 쪽에 해당하는지 코드에서 확인한다.

> **정리**
> 🟡 이번 예시에서 AI가 작성한 스크립트는 파일을 직접 읽어오지 않고, **이미 QGIS 프로젝트에 열려 있는 레이어를 이름으로 찾아** 작업하는 방식으로 구성되어 있었다. 이는 해당 스크립트의 설계 방식일 뿐, PyQGIS 스크립트가 반드시 이렇게 동작해야 한다는 규칙은 아니다 — AI에게 "파일 경로에서 직접 읽어오도록 작성해 달라"고 요청하면 다른 방식의 스크립트를 받을 수도 있다.
>
> 🔵 다만 일반적으로 성립하는 원리는 따로 있다: **어떤 스크립트이든 실행 전에 "이 스크립트가 데이터를 어떤 형태로, 어디서 가져올 것으로 기대하는지"를 먼저 확인해야 한다**는 점이다. 오늘의 스크립트처럼 레이어 이름을 참조하는 방식이라면 아래 순서가 필요하다.
>
> 1. QGIS 실행
> 2. `Layer → Add Layer → Add Vector Layer`(또는 파일 탐색기에서 지도 화면으로 드래그 앤 드롭)로 3개 파일을 순서대로 추가
> 3. 왼쪽 레이어 패널의 이름이 스크립트 안에서 참조하는 이름과 정확히 일치하는지 확인 — 다르다면 레이어를 더블클릭하거나 `F2`로 이름을 바꾸어 맞추거나, AI에게 실제로 표시된 이름을 알려주고 스크립트를 그 이름에 맞게 수정
> 4. 지도 캔버스에 노원구 경계·대피소 점·도로 선이 실제로 그려지는지 눈으로 먼저 확인 — 여기서 보이지 않으면 좌표계 문제일 가능성이 높으므로 1교시로 돌아가 다시 확인
> 5. 여기까지 확인된 뒤에만 Python Console에서 스크립트 실행

## 4교시 — 스크립트 뜯어보기: 격자 간격은 어디서 정해지는가

이제 스크립트가 실행되어 결과가 산출되었다고 가정한다. 결과를 그대로 받아들이기 전에, 스크립트 안에 어떤 값이 고정되어 있는지 코드를 직접 확인한다.

**미션:** 스크립트에서 격자 간격(전차시에 직접 정하였던 값)을 검색한다. 이 값이 QGIS가 노원구의 면적이나 인구밀도를 보고 자동으로 계산하는 값인지, 아니면 스크립트 어딘가에 고정된 숫자로 적혀 있는 값인지 판단한다.

> **힌트**
> `creategrid` 관련 알고리즘을 호출하는 부분을 찾는다. 그 알고리즘에 들어가는 간격 파라미터(`HSPACING`, `VSPACING` 등)의 값이 스크립트 상단 어딘가에 미리 정의된 변수를 그대로 가져다 쓰고 있지는 않은지 확인한다.

> **정리**
> 🔵 격자 간격은 QGIS가 지역 특성을 보고 자동으로 계산해 주지 않는다 — 이는 `native:creategrid` 알고리즘의 일반적인 동작 방식이므로, 다른 스크립트를 받더라도 마찬가지로 성립한다. 어떤 형태로든 이 값은 사람(또는 AI에게 지시한 사람)이 결정하여 코드 어딘가에 넣어야 한다.
>
> 🟡 다만 그 값이 **정확히 아래와 같은 형태로 `GRID_SPACING`이라는 변수에** 담겨 있는 것은 이번 예시 스크립트의 구체적인 모습이다. 학습자가 받은 스크립트에서는 변수명이 다르거나, 함수 인자로 직접 전달되거나, 아예 다른 위치에 있을 수 있다 — 코드 전체에서 `creategrid`(또는 격자 관련 처리 알고리즘) 호출부를 직접 찾아 확인한다.
>
> ```python
> GRID_SPACING = 500  # 후보지 격자 간격(m)
>
> grid = processing.run("native:creategrid", {
>     'TYPE': 0,  # 0 = 사각형
>     'EXTENT': dong_layer.extent(),
>     'HSPACING': GRID_SPACING,
>     'VSPACING': GRID_SPACING,
>     'CRS': dong_layer.crs(),
>     'OUTPUT': 'memory:'
> })
> ```
>
> 🔵 노원구의 면적, 인구밀도, 지형과 무관하게 이 숫자가 그대로 사용된다는 점, 그리고 이 500m가 이전 차시 심화 미션에서 검색을 통해 이미 확인하였듯 민방위 대피시설에 특화된 법적 근거를 가진 숫자가 아니라 도시계획 분야에서 관습적으로 사용되는 도보 서비스권 값(약 400~800m)을 차용한 것이라는 점은, 스크립트의 구체적인 형태와 무관하게 성립하는 사실이다. 즉 **스크립트에 숫자로 고정하는 순간, 그 숫자의 근거는 코드만 보아서는 확인되지 않는다.** 이러한 값은 변수명 옆에 채택 이유를 주석으로 남겨두는 것이 바람직하다.

**미션 2:** 간격을 200m 또는 1000m로 변경하여 다시 실행한다. 후보지 개수와 실행 시간이 어떻게 달라지는지 확인하고, 간격이 촘촘할수록 무조건 더 나은 결과인지 판단한다.

> **힌트**
> 간격을 줄이면 후보지 개수가 늘어나 더 정밀해 보이지만, 계산 시간도 늘어나고 원래 분석 대상이 아니었던 지역(예: 산지)에도 그만큼 더 많은 격자가 생성된다. 간격(spacing)은 "얼마나 촘촘히 볼 것인가"를 정하는 값일 뿐, "애초에 볼 필요가 없는 땅을 걸러낼 것인가"와는 다른 문제이다. 이 둘을 구분하여 기억해 두면 5교시에 도움이 된다.

## 5교시 — 결과를 다시 지도에서 확인하기

스크립트가 계산한 적합도 상위 후보지 목록을 확보하였다. 그러나 전차시에서 학습하였듯, 통계로 산출된 순위를 그대로 신뢰하기 전에 실제 지도에서 육안으로 확인하는 단계가 필요하다.

**미션:** 적합도 상위 5~10개 격자를 QGIS 위성·항공 배경지도(예: `레이어 → XYZ Tiles → 브이월드 위성영상`)에서 확대하여 각각 확인한다. 이상하게 느껴지는 지점이 있는지 판단한다.

3분 정도 확인한 뒤 아래 힌트를 연다.

> **힌트 1**
> 상위권 후보지 중 산 능선이나 숲처럼 보이는 지점이 섞여 있는지 확인한다.

> **힌트 2**
> 전차시에서 인구밀도를 격자에 채워 넣었던 방법을 다시 떠올려 본다 — 행정동 전체 인구를 해당 동의 면적으로 나눈 밀도값을, 격자 중심점이 속한 동 전체에 동일하게 적용하였다. 만약 어떤 동에 산지가 상당 부분 포함되어 있다면 그 산지에 속한 격자에도 동일한 밀도값이 그대로 부여된다. 이것이 결과에 미치는 영향을 판단한다.

> **정리**
> 🔵 행정동 단위로 계산한 인구밀도는 그 동 안의 실제 인구 분포가 균일하다고 가정한다. 동 경계 안에 산지·녹지처럼 인구가 거의 없는 구역이 포함되어 있다면, 그 구역에 속한 격자 역시 동 전체와 같은 밀도값을 그대로 부여받아 실제보다 과대평가될 수 있다. 이는 면적 단위 통계가 갖는 일반적인 한계이다.
>
> 🟡 다만 "노원구의 상위 후보지 중 실제로 산지·숲이 포함되어 있었다"는 것은 이번 예시의 데이터에서 나타난 결과이다. 학습자의 지역·데이터에서는 산지가 아닌 다른 종류의 문제(예: 하천, 군사시설, 기존 건물 등)로 나타날 수도 있고, 이러한 문제가 전혀 발견되지 않을 수도 있다. 중요한 것은 "산지 문제"라는 특정 사례 자체가 아니라, **상위 후보지를 지도에서 직접 육안으로 확인하는 습관**이다.
>
> 🔵 4교시에서 확인하였듯, 격자 간격을 촘촘하게 줄이는 것만으로는 이러한 문제가 해결되지 않는다 — 이는 "얼마나 촘촘히 볼 것인가"가 아니라 "애초에 분석 대상에서 제외해야 할 땅을 걸러내는가"의 문제이기 때문이다.
>
> 이 문제를 즉시 해결하려면 대략 두 방향을 고려할 수 있다.
> - **임야 등 제외 지역 레이어를 추가하여 상위 후보지와 겹치는 격자를 걸러내는 방법**
> - **행정동 단위 대신 더 세밀한 격자 단위 인구 데이터로 교체하는 방법**
>
> 이번 시간 안에 두 방법을 모두 적용하기 어렵다면, 이 문제는 "결과 검증에서 발견하였으나 시간상 다음 기회로 미룬 한계점"으로 기록해 두고 다음 단계로 넘어간다. 다만 발표 자료의 "한계" 섹션에는 이 내용을 반드시 한 줄 남긴다. 예: *"행정동 단위 인구 데이터를 사용한 결과, 임야가 포함된 동에서 인구밀도가 과대평가되는 경향이 발견되었으며, 이는 추후 격자 단위 인구 데이터 또는 임야 제외 처리로 보완이 필요하다."*

## 6교시 — 인쇄조판(Print Layout)까지 자동화하기

지금까지의 스크립트는 격자에 점수를 채워 넣는 단계에서 종료되었다. 그러나 발표 자료에 필요한 것은 화면 캡처가 아니라, 전차시 4교시에서 QGIS 메뉴로 직접 제작하였던 **제목·범례·축척막대가 갖춰진 완성된 지도**이다. 지금까지는 이를 QGIS 화면에서 `프로젝트 → 새 인쇄 조판(New Print Layout)`을 통해 수작업으로 배치하였다.

**미션:** 이 인쇄조판 작업 역시 스크립트로 자동화할 수 있는지 팀에서 먼저 예상해 본다 — 지도의 스타일(단계 구분 시각화), 제목 텍스트, 범례, 축척막대까지 모두 코드로 구성할 수 있다면, 스크립트 실행 한 번으로 최종 발표용 지도 이미지 파일까지 얻을 수 있는지 검토한다.

> **힌트**
> PyQGIS에는 인쇄조판을 다루는 클래스가 별도로 존재한다. `QgsPrintLayout`, `QgsLayoutItemMap`, `QgsLayoutItemLegend`, `QgsLayoutItemScaleBar`, 그리고 완성된 조판을 이미지·PDF 파일로 저장하는 `QgsLayoutExporter`를 검색해 본다. 이름에서 짐작할 수 있듯, 이 클래스들은 각각 "지도 틀 하나", "범례 하나", "축척막대 하나"처럼 인쇄조판 화면에서 직접 끌어다 놓았던 요소 하나하나에 대응한다.

> **정리**
> 🔵 QGIS의 인쇄조판 기능은 PyQGIS API로도 동일하게 제어할 수 있다. 조판을 하나 생성하고, 그 안에 지도·제목·범례·축척막대와 같은 "항목(Layout Item)"을 하나씩 추가한 뒤, 마지막으로 이미지 또는 PDF로 내보내는 순서로 진행된다.
>
> 🟡 아래 코드는 이번 실습에 맞춘 하나의 예시 구조이다. 클래스 이름과 기본 흐름은 QGIS 표준 API에 해당하지만, 좌표·크기·폰트 같은 세부 값은 각자의 화면 배치에 맞게 조정해야 하며, QGIS 버전에 따라 일부 메서드명이 다를 수 있다. 에러가 발생하면 에러 메시지를 AI에게 그대로 제시하고 함께 수정해 나간다.
>
> ```python
> from qgis.core import (
>     QgsProject, QgsPrintLayout, QgsLayoutItemMap, QgsLayoutItemLegend,
>     QgsLayoutItemScaleBar, QgsLayoutItemLabel, QgsLayoutExporter,
>     QgsLayoutPoint, QgsUnitTypes
> )
> from qgis.PyQt.QtCore import QRectF
> from qgis.PyQt.QtGui import QFont
>
> project = QgsProject.instance()
>
> # 1) 새 인쇄조판 생성
> layout = QgsPrintLayout(project)
> layout.initializeDefaults()
> layout.setName("적합도_지도")
> project.layoutManager().addLayout(layout)
>
> # 2) 지도 항목 추가 (적합도 점수가 이미 단계 구분 스타일로 설정된 격자 레이어 사용)
> map_item = QgsLayoutItemMap(layout)
> map_item.attemptSetSceneRect(QRectF(10, 20, 250, 180))
> map_item.setExtent(grid_layer.extent())
> map_item.setLayers([grid_layer])
> layout.addLayoutItem(map_item)
>
> # 3) 제목 텍스트
> title = QgsLayoutItemLabel(layout)
> title.setText("노원구 재난 대피소 입지 적합도 지도")
> title.setFont(QFont("Noto Sans KR", 18))
> title.adjustSizeToText()
> title.attemptMove(QgsLayoutPoint(10, 5, QgsUnitTypes.LayoutMillimeters))
> layout.addLayoutItem(title)
>
> # 4) 범례 (지도 항목과 연결해야 해당 지도의 범례가 표시됨)
> legend = QgsLayoutItemLegend(layout)
> legend.setLinkedMap(map_item)
> legend.attemptSetSceneRect(QRectF(265, 20, 60, 80))
> layout.addLayoutItem(legend)
>
> # 5) 축척막대
> scalebar = QgsLayoutItemScaleBar(layout)
> scalebar.setLinkedMap(map_item)
> scalebar.applyDefaultSize()
> scalebar.attemptMove(QgsLayoutPoint(10, 205, QgsUnitTypes.LayoutMillimeters))
> layout.addLayoutItem(scalebar)
>
> # 6) 이미지 파일로 내보내기
> exporter = QgsLayoutExporter(layout)
> exporter.exportToImage(
>     "output/노원구_적합도_지도.png",
>     QgsLayoutExporter.ImageExportSettings()
> )
> ```

**미션 2:** 스크립트를 실행하여 지도 이미지 파일을 얻었다면, 그 결과를 전차시 4교시에서 수작업으로 제작하였던 지도와 나란히 놓고 비교한다. 제목 위치, 범례 내용, 색상 구분이 의도한 대로 나타났는지 확인한다. 차이가 있다면 코드의 어느 줄(좌표값, 폰트, 연결된 레이어 등)을 수정해야 할지 스스로 짚어보고, 필요한 경우 AI에게 구체적으로 수정을 요청한다.

> **정리**
> 🔵 자동화된 지도 출력이 한 번에 완벽하게 산출되는 경우는 드물다. 좌표·크기 값을 조금씩 조정하며 여러 차례 다시 내보내는 것이 정상적인 과정이다. 이는 3교시에서 경험한 "요청 → 실행 → 에러/이상 결과 → 재요청"의 흐름이 인쇄조판 단계에서도 동일하게 반복되는 것에 해당한다.
>
> 🟡 다만 "격자 레이어에 단계 구분 스타일이 이미 적용되어 있어야 지도에 색상이 제대로 나타난다"는 점은 이번 스크립트 구조에 국한된 전제이다. 스타일링 자체를 코드로 자동화하고자 한다면(`QgsGraduatedSymbolRenderer` 등), 이 부분도 별도로 AI에게 요청하여 스크립트에 추가할 수 있다 — 이번 실습에서는 전차시에 이미 제작한 스타일을 그대로 재사용하는 방식으로 진행한다.

## 7교시 — 스크립트를 QGIS 안에서 "도구"처럼 쓰기

지금까지는 매번 Python Console을 열고 코드 전체를 붙여넣어 실행하였다. 스크립트가 안정적으로 완성되었다면, 이제 매번 붙여넣지 않고도 사용할 수 있는 방법을 검토할 차례이다.

**미션:** 스크립트를 QGIS 메뉴에서 바로 실행할 수 있도록 만드는 방법에는 난이도가 다른 몇 단계가 있다. 아래 세 가지 중 오늘 스크립트의 구조(레이어 세 개를 입력받아 계산하고 지도를 출력)에 가장 적합한 방법이 무엇일지 팀에서 먼저 예상한다.

- **방법 A** — Python Console 편집기에 `.py` 파일로 저장해 두고 실행 버튼만 누르는 방법
- **방법 B** — Processing Toolbox에 나만의 도구로 등록하는 방법
- **방법 C** — 툴바 아이콘과 메뉴가 있는 완전한 플러그인을 제작하는 방법

> **힌트**
> 오늘 스크립트가 수행하는 작업을 다시 떠올려 본다 — "레이어를 입력받아 계산하고 결과를 출력한다"는 구조이다. 이전 차시에 Processing Toolbox에서 검색하여 사용하였던 QGIS 기본 도구들(격자 만들기, 최근접 지점 결합 등)도 동일하게 "입력을 받아 처리하고 출력을 내는" 구조였다. 이 구조와 가장 유사한 위치가 QGIS의 어디에 이미 존재하였는지 떠올려 본다.

> **정리**
> 세 방법은 난이도와 목적이 다르다.
>
> | 방법 | 무엇을 하는가 | 실행 방식 | 적합한 경우 |
> |---|---|---|---|
> | A. Console 편집기 저장 | 코드를 `.py` 파일로 저장 | Python Console을 열고 Show Editor의 ▶ Run Script 버튼 | 나 혼자 반복적으로 실행하는 경우 |
> | B. Processing Toolbox 스크립트 등록 | `QgsProcessingAlgorithm`을 상속하는 형태로 스크립트를 감싸서 등록 | Toolbox 목록에 도구로 나타나고, 다른 QGIS 기본 도구처럼 대화상자에서 레이어를 선택해 실행 | 지금 스크립트처럼 "레이어 입력 → 처리 → 출력" 구조인 경우 |
> | C. 완전한 플러그인 | Plugin Builder로 폴더 구조 생성, 툴바 아이콘·메뉴 항목까지 구현 | 툴바 아이콘 클릭 한 번으로 실행 | 다른 사람에게 배포하거나 지속적으로 유지보수할 도구가 필요한 경우 |
>
> 🔵 오늘 스크립트처럼 "레이어를 입력받아 계산하고 출력하는" 구조에는 **방법 B(Processing Toolbox 스크립트 등록)**가 가장 적합하다. 레이어 선택과 출력 경로 지정을 GUI 대화상자로 처리할 수 있어, 3교시에서 경험한 "레이어 이름이 스크립트와 일치하지 않아 발생하는 에러" 유형의 문제가 크게 줄어든다. 방법 C는 배포까지 고려할 때 적합하지만, 현재 단계에서는 다소 과한 방법일 수 있다.

**미션 2:** 방법 B로 등록한다. `Processing Toolbox → Scripts → Create New Script`(또는 상단 메뉴의 `Tools → Create New Script`)로 편집기를 연 뒤, 지금까지 작성한 스크립트를 AI에게 제시하며 "이 스크립트를 `QgsProcessingAlgorithm` 클래스 형태로 변환해 달라"고 요청한다.

> **힌트**
> `QgsProcessingAlgorithm`으로 감싼 스크립트는 일반적으로 아래 구성 요소를 포함한다. AI가 작성한 코드에 이 항목들이 있는지 확인한다.
> - `initAlgorithm()` — 입력 레이어·출력 경로 같은 "파라미터"를 정의하는 부분
> - `processAlgorithm()` — 실제 계산 로직 (지금까지 작성한 스크립트의 핵심 부분이 여기로 들어간다)
> - `name()`, `displayName()` — Processing Toolbox 목록에 표시될 이름

> **정리**
> 🔵 `QgsProcessingAlgorithm`은 QGIS 기본 도구들도 내부적으로 사용하는 표준 구조이다. 계산 로직 자체(격자 생성, 조인, 정규화·가중합, 6교시의 지도 출력)는 그대로 유지하고, "입력을 어떻게 받을지"와 "출력을 어디로 내보낼지"만 정해진 형식에 맞게 선언하면 된다.
>
> 🟡 클래스 구조의 큰 틀은 QGIS 표준 API에 해당하지만, 정확한 메서드 시그니처나 세부 문법은 QGIS 버전에 따라 다소 다를 수 있다. 저장(편집기의 저장 버튼 또는 `Ctrl+S`)한 뒤 Processing Toolbox 목록에 도구 이름이 나타나는지 확인하고, 더블클릭하여 실행 대화상자가 나타나는지 확인한다. 이 단계부터는 레이어 이름을 코드에 미리 적어두는 대신, 실행할 때마다 대화상자에서 직접 레이어를 선택하는 방식으로 전환된다 — 3교시에서 다룬 "레이어를 이름으로 찾는 방식" 문제를 근본적으로 우회하는 방법이기도 하다.

## 오늘의 체크리스트

- [ ] 실행 전 세 레이어의 좌표계 확인 및 필요시 통일
- [ ] 속성 테이블·레이어 패널에서 실제 필드명과 레이어 이름 확인 및 기록
- [ ] 스크립트가 파일이 아닌 "열려 있는 레이어 이름"을 참조한다는 것을 에러를 통해 확인
- [ ] 격자 간격이 자동 계산이 아닌 스크립트 내 고정값임을 코드에서 확인
- [ ] 격자 간격을 변경하여 실행하고, 간격 조정과 지역 필터링이 서로 다른 문제임을 구분

- [ ] 스크립트 실행만으로 발표용 지도 이미지 파일 생성 확인
- [ ] 자동 생성된 지도와 수작업 지도의 비교 및 코드 수정
- [ ] 스크립트 재사용 방식(Console 저장/Processing Toolbox 등록/플러그인) 결정 및 근거 기록

- [ ] 발견한 문제 중 해결한 것과 미룬 것 구분 정리 (다음 발표 자료의 "한계" 섹션에 필요)
