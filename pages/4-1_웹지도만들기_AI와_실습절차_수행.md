# 프로젝트3 실습 절차 — AI와 함께 수행하기

이 문서는 학습 자료(`웹지도_만들기.md`)의 실행 절차를, 학습자가 AI(Claude 등)에게 질문하며 실제로 채워나가는 과정을 보여준다. 각 단계마다 AI에게 던질 수 있는 질문 예시와, 그 답을 바탕으로 결정에 이르는 흐름을 함께 제시한다. 최종적으로 채워진 결정사항 자체는 `웹지도만들기_실습절차_예시.md`에서 확인할 수 있다.

---

## 1. 웹지도 제작 실행 절차

### 1) 웹지도 제작 대상 결정
- **AI에게 물어볼 질문**: "지금까지 만든 프로젝트 결과물 중 어떤 걸 웹지도로 만들면 좋을까?"
- **흐름**: AI가 데이터 형태(포인트/폴리곤)와 결과물의 메시지 전달력을 비교해주면, 프로젝트1(대피소 입지 적합성 분석)의 적합도 점수를 웹지도 대상으로 선택한다.

### 2) 웹지도 표현 방식 결정
- **AI에게 물어볼 질문**: "QGIS2Web으로 자동 변환하는 것과, AI에게 직접 Leaflet 코드를 요청하는 것 중 뭐가 나을까?"
- **흐름**: AI가 각 방식의 장단점(속도 vs 커스터마이징 자유도)을 비교해주면, 두 방식을 모두 진행해 직접 비교해보기로 한다.

### 3) 팝업·색상 표현 필드 결정
- **AI에게 물어볼 질문**: "웹지도 팝업에 어떤 필드를 넣는 게 좋을까? 지금 필드가 여러 개인데."
- **흐름**: AI가 "팝업에는 핵심 메시지 하나만 남기는 것이 낫다"고 안내하면, `suitability` 필드만 남기고 나머지 중간 계산 필드는 제외하기로 결정한다.

### 4) 좌표계 확인
- **AI에게 물어볼 질문**: "지금 EPSG:5179로 되어 있는데, 웹지도로 만들 때 좌표계를 바꿔야 해?"
- **흐름**: AI가 GeoJSON 표준이 좌표계를 EPSG:4326(WGS84)으로 고정한다는 점과, 배경 타일 자체는 내부적으로 EPSG:3857(Web Mercator)을 쓰지만 이 변환은 라이브러리가 자동 처리해준다는 점을 설명해주면, GeoJSON 내보내기 시 좌표계를 EPSG:4326으로 재투영하기로 한다.
- **QGIS 실습**: 레이어 우클릭 → `Export → Save Features As` → Format: GeoJSON, CRS: EPSG:4326 선택 후 저장한다.

### 5) AI 요청 프롬프트 구성
- **AI에게 물어볼 질문**: "Leaflet 지도를 만들어달라고 요청할 때 어떤 정보를 포함해야 결과가 잘 나올까?"
- **흐름**: AI가 역할·맥락·요청·제약을 구분해 구체화하는 프롬프트 구조를 제안해주면, 이 형식에 맞춰 `suitability` 필드의 의미, 색상 규칙(노랑→빨강), 팝업 표시 내용, 단일 HTML 파일 제약을 포함한 프롬프트를 구성한다.
- **실습**: 완성한 프롬프트에 GeoJSON 파일을 첨부해 AI에게 요청하고, 받은 HTML 코드를 저장해 브라우저로 확인한다.

### 6) 결과 비교 방식 결정
- **AI에게 물어볼 질문**: "QGIS2Web 결과와 AI가 만든 코드를 비교하려면 어떤 기준으로 봐야 할까?"
- **흐름**: AI가 걸린 시간, 색상 표현, 범례, 팝업 내용, 코드 이해도, 커스터마이징 자유도, 재사용성 등 비교 축을 제안해주면, 이를 표로 정리해 실제 경험한 내용을 기록한다.

## 2. 인터랙션 구현 및 배포 실행 절차

### 1) 추가할 인터랙션 기능 결정
- **AI에게 물어볼 질문**: "지금 만든 웹지도에 어떤 인터랙션 기능을 추가하면 좋을까?"
- **흐름**: AI가 필터·검색·툴팁 등 여러 옵션을 제시해주면, "상위 후보지만 골라보기"에 가장 유용한 적합도 구간 슬라이더를 채택한다.

### 2) 수정 요청 방식 결정
- **AI에게 물어볼 질문**: "지금 파일에 필터 기능만 추가하고 싶은데, 어떻게 요청해야 기존 코드가 그대로 유지될까?"
- **흐름**: AI가 "고쳐줘"라고만 요청하면 코드 전체가 재작성될 수 있다는 점과, 기존 코드 전체를 맥락으로 붙여넣고 "기존 코드 구조는 유지"라는 제약을 명시하는 방법을 설명해주면, 이 형식으로 프롬프트를 구성한다.
- **실습**: 기존 `nowon_leaflet_map.html` 코드 전체를 맥락에 붙여넣고, 위 형식의 프롬프트로 필터 기능을 요청한다.

### 3) 배포 플랫폼 결정
- **AI에게 물어볼 질문**: "이 웹지도를 인터넷에 무료로 배포하려면 어떤 방법이 있어?"
- **흐름**: AI가 GitHub Pages 등 정적 사이트 호스팅 옵션과 각각의 조건(가입 여부, 비용, 설정 난이도)을 비교해주면, 별도 가입 없이 기존 GitHub 계정으로 바로 사용할 수 있는 GitHub Pages를 선택한다.

### 4) 업로드 파일 범위 결정
- **AI에게 물어볼 질문**: "깃허브에 올릴 때 개인정보나 민감한 데이터 관련해서 조심할 게 있을까?"
- **흐름**: AI가 원본 GeoJSON·CSV의 민감 필드(관리번호, 시설위치, 수용인원 등)와 API 키가 코드에 노출될 경우의 위험을 짚어주면, 정제된 웹지도 HTML만 게시하고 원본 데이터·키가 포함된 스크립트는 게시하지 않기로 결정한다.
- **QGIS/실습 확인**: 게시 전 파일 목록을 다시 확인해, 원본 CSV·GeoJSON이 실수로 포함되지 않았는지 점검한다.

### 5) 반응형·사용성 검증 방법 결정
- **AI에게 물어볼 질문**: "배포한 웹지도가 스마트폰에서도 잘 보이는지, 실제로 잘 쓸 수 있는지 어떻게 확인해야 할까?"
- **흐름**: AI가 반응형 체크 항목(화면에 꽉 차는지, 슬라이더가 잘리는지, 터치 확대·축소가 되는지)과 사용성 테스트 과업 설계 방법(구체적인 과업 하나를 주고 관찰하기)을 제안해주면, 이를 그대로 적용해 스마트폰으로 직접 확인하고 동료에게 테스트를 요청한다.

## 정리

이 과정에서 공통적으로 드러나는 흐름은 다음과 같다.

1. 학습자가 진행 중인 화면·코드·아이디어를 AI에게 그대로 보여주고 질문한다.
2. AI가 여러 선택지의 근거와 장단점을 비교해 설명한다.
3. 학습자는 그 설명을 바탕으로 최종 결정을 내리고, 결정의 이유를 함께 기록한다.

AI가 대신 결정해주는 것이 아니라, 결정에 필요한 근거를 학습자가 판단할 수 있도록 정리해주는 역할을 한다는 점이 이 과정의 핵심이다. 특히 수정 요청(2절 2번)의 경우, AI의 설명을 듣고 끝내는 것이 아니라 "기존 코드 구조 유지"라는 제약을 실제 프롬프트에 반영하는 것까지가 결정에 해당한다.
