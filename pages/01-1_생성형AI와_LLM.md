## 제1절. 생성형 AI (Generative AI)

### 1. 정의

생성형 AI란 텍스트, 이미지, 코드, 음악, 영상 등 새로운 콘텐츠를 생성하는 인공지능(Artificial Intelligence, AI) 기술을 통칭하는 상위 개념이다. LLM은 생성형 AI 가운데 텍스트(언어) 영역을 담당하는 하위 범주에 해당한다.

```
생성형 AI (Generative AI)
 ├─ LLM (텍스트 생성 · 이해)
 ├─ 이미지 생성 모델 (Diffusion 모델 등)
 ├─ 음성 · 음악 생성 모델
 └─ 영상 생성 모델
```

### 2. 생성형 AI가 가져온 변화

생성형 AI의 확산은 다음과 같은 변화를 가져왔다.

- 콘텐츠 제작의 진입 장벽 하락: 비전문가도 결과물을 생성할 수 있게 되었다.
- 반복 작업의 자동화: 초안 작성, 요약, 코드 스캐폴딩 등이 자동화되었다.
- 새로운 상호작용 방식의 등장: "프롬프트"라는 자연어 기반 명령 방식이 보편화되었다.

### 3. 대표적인 생성형 AI 분류 (2026년 기준)

생성형 AI는 만들어내는 콘텐츠의 형태에 따라 다음과 같이 분류할 수 있다.

| 분류 | 설명 | 대표 사례 |
|---|---|---|
| 텍스트 생성 (LLM 기반) | 대화, 글쓰기, 분석 등 언어 관련 작업을 수행한다. | ChatGPT(OpenAI), Claude(Anthropic), Gemini(Google) |
| 이미지 생성 | 텍스트나 이미지를 입력하면 새로운 이미지를 생성한다. | Midjourney, DALL-E, Flux.1(Black Forest Labs), Stable Diffusion, Adobe Firefly |
| 영상 생성 | 텍스트나 이미지를 기반으로 동영상을 생성한다. | Sora 2(OpenAI), Veo 3.1(Google), Runway Gen-4, Kling 3.0 |
| 음악·음성 생성 | 음악을 작곡하거나 음성을 복제·합성한다. | Suno, Udio(음악), ElevenLabs(음성 복제·합성) |
| 코드 생성 | LLM의 하위 활용 형태로, 프로그래밍 코드를 생성·보완한다. | GitHub Copilot, Cursor, Claude Code |

2026년 기준 이미지 생성 분야에서는 오픈소스 모델인 Flux.1이 사실감과 타이포그래피 인식에서 강점을 보이며 기존 Midjourney·DALL-E 중심의 구도를 재편하였고, Adobe Firefly는 라이선스가 확실한 데이터만으로 학습되어 상업적으로 안전하게 사용할 수 있는 기업용 도구로 자리잡았다. 영상 생성 분야는 생성형 AI 카테고리 중 가장 빠르게 발전하고 있는 영역으로 평가되며, Veo 3.1은 시각 콘텐츠와 동기화된 오디오를 후처리 없이 네이티브로 생성하는 것이 특징이고, Runway Gen-4는 생성보다는 영상의 특정 부분을 편집하는 기능에 강점이 있어 실제 제작 현장에서 널리 활용되고 있다. 음악 분야에서는 Suno와 Udio가 대표적이며, 음성 복제·합성 분야에서는 ElevenLabs가 사실상의 표준으로 자리잡았다.

### 4. 생성형 AI와 LLM의 관계

생성형 AI와 LLM은 대등한 개념이 아니라 상위 개념과 하위 개념의 관계에 있다. 생성형 AI는 새로운 콘텐츠를 만들어내는 AI 기술 전체를 가리키는 범주이며, LLM은 그중에서도 텍스트(언어)를 다루는 하위 기술이다. 대량의 텍스트 데이터를 학습하여 언어를 이해하고 생성하는 능력을 지닌 모델이 LLM에 해당한다.

이러한 관계에서 다음 두 가지 명제가 성립한다.

- 모든 LLM은 생성형 AI에 속하지만, 모든 생성형 AI가 LLM인 것은 아니다.
- 예를 들어 이미지를 생성하는 모델(Midjourney, Stable Diffusion 등)은 생성형 AI에 해당하지만 LLM은 아니다. 반면 텍스트를 생성하는 모델(ChatGPT, Claude 등)은 생성형 AI이면서 동시에 LLM에 해당한다.

## 제2절. LLM (Large Language Model, 거대언어모델)

### 1. 정의

LLM이란 방대한 양의 텍스트 데이터를 학습하여 다음에 올 단어(토큰)를 예측하는 방식으로 작동하는 대규모 신경망 모델을 말한다. LLM은 Transformer라는 구조를 기반으로 하며, 문장을 이해하고 생성하는 능력을 갖추고 있다는 점이 특징이다.

### 2. 핵심 용어

| 용어 | 설명 |
|---|---|
| 토큰(Token) | LLM이 텍스트를 처리하는 최소 단위. 단어보다 작을 수도, 클 수도 있다. |
| 파라미터(Parameter) | 모델이 학습을 통해 조정하는 가중치 값. 일반적으로 파라미터 수가 많을수록 더 복잡한 언어 패턴을 학습할 수 있다. |
| 사전학습(Pre-training) | 인터넷 규모의 대량 텍스트로 언어 패턴을 학습하는 1단계 과정이다. |
| 파인튜닝/정렬(Fine-tuning, Alignment) | 특정 목적(대화, 지시 이행, 안전성 등)에 맞게 모델을 추가로 조정하는 2단계 과정이다. |
| 컨텍스트 윈도우(Context Window) | 모델이 한 번에 참고할 수 있는 입력 텍스트의 최대 길이를 말한다. |
| 환각(Hallucination) | LLM이 사실이 아닌 정보를 그럴듯하게 생성하는 현상이다. LLM을 활용할 때 반드시 유의해야 하는 한계점이다. |

### 3. 대표적인 LLM 종류 (2026년 기준)

LLM은 개발 주체와 공개 방식에 따라 크게 상용 폐쇄형 모델, 오픈소스 모델, 국산(한국어 특화) 모델로 구분할 수 있다.

| 분류 | 설명 | 대표 사례 |
|---|---|---|
| 상용 폐쇄형(Closed-source) 모델 | 기업이 개발하여 API·서비스 형태로 제공하며, 가중치가 공개되지 않는다. | GPT 계열(OpenAI), Claude 계열(Anthropic), Gemini 계열(Google), Grok(xAI) |
| 오픈소스(Open-source) 모델 | 가중치가 공개되어 있어 개발자가 직접 내려받아 실행하거나 변형할 수 있다. | Llama 계열(Meta), Mistral 계열(Mistral AI), DeepSeek 계열 |
| 국산(한국어 특화) 모델 | 한국어와 국내 데이터에 최적화된 모델로, 국내 기업이 개발한다. | 하이퍼클로바X(네이버), 엑사원(LG), 에이닷X(SK텔레콤), 카나나(카카오), 솔라(업스테이지) |

2026년 기준 GPT, Claude, Gemini 등 상용 모델은 대화, 추론, 장문 처리 등에서 각기 다른 강점을 보이며 빠른 속도로 새로운 버전이 출시되고 있다. 국산 모델 가운데 하이퍼클로바X는 한국어 데이터 학습량이 GPT-3 대비 약 6,500배에 달하는 것으로 알려져 있으며, 한국어 특화 설계로 국내용 품질에서 강점을 보인다는 평가를 받는다. 국산 LLM은 금융·공공·의료처럼 보안과 데이터 주권이 중요한 분야의 기업용(B2B) 도입에서 특히 수요가 크다.

### 4. 대표적인 활용 형태

LLM은 다음과 같은 분야에서 활용된다.

- 챗봇 및 어시스턴트(질의응답, 요약, 번역)
- 코드 생성 및 코드 리뷰
- 문서 작성 보조
- 데이터 분석 보조

## 제3절. 바이브 코딩 (Vibe Coding)

### 1. 정의와 유래

바이브 코딩이란 개발자가 코드를 직접 작성하지 않고, 자연어로 원하는 바를 설명하면 AI가 코드를 생성하는 개발 방식을 말한다. 코드의 세부 작동 원리를 깊이 이해하지 않고도 결과물을 만들어낼 수 있다는 점이 기존의 AI 코드 어시스턴트와 구별되는 특징이다. 이 용어는 개발자가 사전에 구체적인 논리를 구축하지 않고 직관에 따라 큰 그림만 제시한다는 뜻에서 '느낌'을 의미하는 '바이브(vibe)'라는 이름이 붙었으며, 2025년 2월 안드레 카파시(Andrej Karpathy)가 소셜미디어(X)를 통해 처음 제시한 개념이다.

카파시는 OpenAI 공동창립자이자 전 Tesla AI 리더 출신의 컴퓨터 과학자로서, 자신의 접근 방식을 "실제로 코딩은 아니다. 그저 사물을 보고, 말하고, 실행하고, 복사해서 붙여넣기만 하면 대부분 작동한다"는 식으로 설명하였다. 이 개념은 2025년 3월 Merriam-Webster 사전에 "속어 및 트렌드" 명사로 등재되었으며, 콜린스 사전은 바이브 코딩을 2025년 올해의 단어로 선정한 바 있다.

한편 개발자 사이먼 윌리슨(Simon Willison)은 이 개념을 보다 엄밀하게 규정하였다. 그에 따르면 진정한 의미의 바이브 코딩이란 LLM이 작성한 코드를 검토하지 않고 소프트웨어를 만드는 것을 가리키며, 모든 줄을 읽고 테스트하고 이해한다면 이는 AI를 단순한 타이핑 보조 도구로 활용하는 것에 불과하다고 구분하였다.

### 2. 작동 방식

바이브 코딩은 다음과 같은 순서로 진행된다.

1. 목표를 평이한 언어로 설명한다.
2. AI가 코드를 생성한다.
3. 실행 결과를 확인한다.
4. 결과에 따라 추가 지시를 반복한다.

### 3. 적합한 상황과 한계

바이브 코딩은 요구사항이 불확실하고 빠르게 실체를 보여주어야 하는 MVP(Minimum Viable Product, 최소기능제품) 이전 단계, 그리고 고객 피드백을 위한 프로토타입 제작에 적합한 방식으로 평가된다.

다만 다음과 같은 한계가 지적된다. 2025년 발표된 연구에 따르면 AI가 생성한 코드 샘플 중 상당수가 보안 결함을 포함하고 있었으며, 중복되고 리팩터링되지 않은 코드가 늘어나는 경향이 확인되었다. 카파시 본인도 이 방식을 "버려도 되는 주말 프로젝트용"으로 한정하여 제시한 바 있다.

### 4. 2026년 현재 동향

2026년 기준 개발자의 84%가 이미 AI 코딩 도구를 사용하고 있거나 사용을 계획하고 있으며, 일반적인 작업에서 3~5배의 생산성 향상이 보고되고 있다. IBM은 바이브 코딩을 아직 명확하게 정의되지 않은 신조어로 평가하면서도, 소프트웨어 엔지니어링이 엄격한 수동 코딩 방식에서 벗어나 유연하고 AI 중심적인 개발로 변화하는 흐름의 최전선에 있다고 평가하고 있다.

## 제4절. 에이전트 코딩 (Agentic Coding)

### 1. 정의

에이전트 코딩(에이전틱 코딩)이란 AI 에이전트가 목표를 부여받은 뒤 스스로 계획을 세우고 코드 작성, 실행, 테스트, 수정까지의 과정을 반복하는 개발 방식을 말한다. 전통적인 AI 코딩 어시스턴트가 사용자의 입력을 기다렸다가 반응하는 것과 달리, 에이전트형 코딩 도구는 상위 수준의 지시를 받아 스스로 실행한다는 차이가 있다. 에이전트는 목표를 이해하고 이를 단계별로 분해한 뒤 작업 완료에 필요한 행동을 직접 수행하는데, 이러한 특성은 수동적인 컨설턴트보다는 숙련된 계약자에 가까운 존재로 비유된다.

### 2. 바이브 코딩과의 비교

바이브 코딩과 에이전트 코딩의 가장 결정적인 차이는 인간 개입의 정도와 방식에 있다. 바이브 코딩은 인간 중심의 상호작용을 특징으로 하며, 개발자가 대화를 통해 아이디어를 구체화하는 과정에서 지속적인 개입이 요구되고, 각 작업의 품질을 개발자가 직접 감독한다. 반면 에이전트 코딩은 목표 중심의 자율적 작업 수행에 초점이 있으며, 개발자는 시스템 차원의 감독 위주로 관여하고 중간·최종 결과물만을 점검하는 역할을 수행한다.

| 구분 | 바이브 코딩 | 에이전트 코딩 |
|---|---|---|
| 상호작용 모델 | 인간 중심 상호작용. 대화를 통해 아이디어를 구체화한다. | 목표 중심의 자율적 작업 수행 |
| 개발자 개입 | 지속적인 개입이 필요하며, 각 작업의 품질을 개발자가 직접 감독한다. | 시스템 차원의 감독 위주이며, 중간·최종 결과물만을 점검한다. |
| 실행 방식 | 사람이 그때그때 즉흥적으로 지시한다. | 목표를 한 번 부여하면 AI 에이전트가 스스로 도구를 호출하며 작업을 완료한다. |
| 도구 사용 | 제한적이며 주로 코드 생성에 국한된다. | 터미널, 파일 시스템, 테스트 러너와 같은 도구를 직접 호출한다. |

### 3. 개념 간의 위계

바이브 코딩과 에이전트 코딩은 완전히 별개의 개념이 아니라 연속선상에 있는 개념으로 이해할 수 있다. AI 에이전트는 특정 환경을 인지하고 추론하여 목표 달성을 위해 행동하는 자율적 지능형 시스템의 기본 형태이며, 에이전틱 AI는 여기서 더 나아가 스스로 복잡한 목표를 설정하고 다단계 계획을 수립하며 여러 에이전트나 외부 도구를 활용하여 자율적으로 실행·개선하는 시스템을 말한다. 즉 바이브 코딩이 큰 틀에서의 트렌드 내지 문화적 용어라면, 에이전트 코딩은 그 안에서 에이전트 기술을 실제로 구현한 실행 방식에 해당한다고 정리할 수 있다.

### 4. 실무 설계 요소: agents.md

에이전트 코딩이 확산됨에 따라 에이전트에게 규칙과 역할을 명시하는 설정 파일 작성 관행이 자리잡고 있다. 효과적인 agents.md 파일은 실행 가능한 명령을 앞부분에 배치하고, 추상적인 설명보다 구체적인 코드 예시를 제공하며, 에이전트가 수행해야 할 일과 절대 하지 말아야 할 경계를 명확히 규정한다는 공통점을 지닌다. 분석된 성공적인 사례들은 에이전트를 '제너럴리스트'가 아닌 '스페셜리스트'로 정의하고 있었다.

- 실패 사례: "당신은 유능한 코딩 어시스턴트입니다." (모호한 지침)
- 성공 사례: "당신은 React 컴포넌트의 테스트만 작성하며, 소스 코드는 절대 수정하지 않는 테스트 엔지니어입니다." (구체적 역할 부여)

## 제5절. 네 개념의 위계 정리

| 개념 | 층위 | 정의 |
|---|---|---|
| 생성형 AI | 최상위 개념 | 새로운 콘텐츠(텍스트·이미지·코드 등)를 생성하는 AI 기술 전반 |
| LLM | 생성형 AI의 하위 기술 | 텍스트를 이해하고 생성하는 대규모 언어 모델 |
| 바이브 코딩 | LLM의 활용 방식(문화적 트렌드) | 자연어로 지시하여 AI가 코드를 작성하게 하고, 세부 검토 없이 결과를 수용하는 개발 방식 |
| 에이전트 코딩 | 바이브 코딩의 기술적 구현체 | AI 에이전트가 목표를 부여받아 계획·실행·테스트·수정을 자율적으로 반복하는 개발 방식 |

## 단원 정리

1. LLM과 생성형 AI는 기술적 기반이 되는 개념이며, 바이브 코딩과 에이전트 코딩은 그 기술을 실제 개발 워크플로우에 적용한 방식이라는 층위상의 차이가 있다.
2. 바이브 코딩은 속도와 몰입에 중점을 두는 반면, 에이전트 코딩은 자율성과 도구 사용에 중점을 둔다.
3. 두 방식 모두 검토 없는 전적인 신뢰는 보안 결함 및 품질 부채로 이어질 수 있다는 공통된 한계가 지적된다. 따라서 실무에서는 '빠른 탐색(바이브 코딩·에이전트 코딩) 이후 속도를 늦춘 검증'이라는 절차가 권장된다.
4. 실무 확산과 더불어 agents.md와 같이 에이전트에게 규칙을 명시하는 관행이 새로운 표준으로 자리잡는 추세이다.

## 제6절. 생성형 AI '모델'과 '도구'의 구분

### 1. 정의

생성형 AI와 관련하여 '모델'과 '도구'라는 용어는 자주 혼용되지만 서로 다른 층위를 가리킨다.

- **생성형 AI 모델(Model)**: 콘텐츠를 생성하는 핵심 엔진 내지 알고리즘 자체를 가리킨다. 학습된 파라미터와 아키텍처(Transformer, Diffusion 등)로 구성되며, 개발자가 애플리케이션을 만들 때 가져다 쓰는 기술적 구성요소에 해당한다. 예: GPT-4, Claude, Gemini(텍스트 생성 모델), Stable Diffusion, DALL-E(이미지 생성 모델).
- **생성형 AI 도구(Tool/Application)**: 모델을 감싸서 사람이 실제로 사용할 수 있게 만든 제품 내지 서비스를 가리킨다. 채팅 인터페이스, 웹/앱 사용자 인터페이스(User Interface, UI), API(Application Programming Interface) 연동, 부가 기능(파일 업로드, 검색 등)까지 포함한 완성된 형태이다. 예: ChatGPT(웹앱), Claude.ai(웹앱), Cursor(코딩 에디터), Notion AI(문서 도구).

### 2. 관계

```
생성형 AI 도구(Tool) = 생성형 AI 모델(엔진) + 사용자 인터페이스 + 부가 기능
```

모델은 '무엇으로 생성하는가'라는 기술적 핵심을 가리키고, 도구는 '어떻게 사용하는가'라는 사용자 접점을 가리킨다. 하나의 모델은 여러 도구에 동시에 탑재될 수 있다. 예컨대 Claude 모델은 Claude.ai 웹앱, Claude 데스크톱 앱, Claude API를 통한 서드파티 애플리케이션 등 서로 다른 여러 도구의 형태로 제공된다.

### 3. 적용 사례: 클로드(Claude)

'클로드'라는 명칭은 맥락에 따라 모델과 도구 양쪽을 모두 가리킬 수 있다.

- 모델로서의 클로드: Claude Sonnet 5, Claude Opus 5와 같은 이름은 텍스트를 이해하고 생성하는 핵심 엔진, 즉 모델을 가리킨다.
- 도구로서의 클로드: claude.ai 웹/앱 인터페이스는 Claude 모델을 감싸 채팅 UI, 파일 업로드, 검색, 아티팩트 생성 등의 부가 기능을 더한 도구를 가리킨다.

## 학습 확인 퀴즈

### 문제 1. 생성형 AI와 LLM의 관계에 대한 설명으로 옳은 것은?

① 생성형 AI와 LLM은 서로 대등한 별개의 개념이다
② LLM은 생성형 AI의 하위 개념이며, 텍스트 영역을 담당한다
③ 생성형 AI는 LLM의 하위 개념이며, 이미지 영역만 담당한다
④ LLM은 생성형 AI가 발전하기 이전에 사라진 기술이다

> **정답: ②**
> 생성형 AI는 텍스트·이미지·음악·영상 등 콘텐츠 생성 기술 전체를 아우르는 상위 개념이고, LLM은 그중 텍스트(언어)를 다루는 하위 기술이다.

### 문제 2. 다음 중 생성형 AI에는 해당하지만 LLM은 아닌 것은?

① ChatGPT
② Claude
③ Stable Diffusion
④ GPT-4

> **정답: ③**
> Stable Diffusion은 이미지를 생성하는 모델로 생성형 AI에는 해당하지만, 텍스트를 다루는 LLM은 아니다. ChatGPT, Claude, GPT-4는 텍스트 생성을 다루므로 생성형 AI이면서 동시에 LLM이다.

### 문제 3. 생성형 AI '모델'과 생성형 AI '도구'의 차이를 가장 잘 설명한 것은?

① 모델은 사용자 인터페이스이고, 도구는 학습된 파라미터를 가리킨다
② 모델은 콘텐츠를 생성하는 핵심 엔진이고, 도구는 모델을 감싸 사람이 실제로 사용할 수 있게 만든 제품이다
③ 모델과 도구는 완전히 동일한 개념으로 구분할 필요가 없다
④ 모델은 개발자용이고, 도구는 항상 무료로 제공된다

> **정답: ②**
> 모델은 Transformer 등 아키텍처와 학습된 파라미터로 구성된 핵심 엔진(예: GPT-4, Claude)이며, 도구는 그 모델에 채팅 UI, 파일 업로드 등 부가 기능을 더해 사람이 바로 쓸 수 있게 만든 제품(예: ChatGPT 웹앱, Claude.ai)이다.

### 문제 4. "클로드(Claude)"라는 이름에 대한 설명으로 가장 적절한 것은?

① 클로드는 오직 모델만을 가리키며 도구로는 존재하지 않는다
② 클로드는 오직 도구(채팅 앱)만을 가리키며 모델은 별도의 이름을 쓴다
③ 클로드는 맥락에 따라 모델(예: Claude Sonnet 5)과 도구(예: claude.ai 채팅 인터페이스)를 모두 가리킬 수 있다
④ 클로드는 이미지 생성 전용 모델이다

> **정답: ③**
> Claude Sonnet 5 같은 이름은 텍스트 생성의 핵심 엔진인 '모델'을 가리키고, claude.ai 웹/앱 인터페이스는 그 모델을 감싸 채팅 UI와 부가 기능을 더한 '도구'를 가리킨다. 즉 두 의미 모두로 쓰인다.

### 문제 5. 같은 Claude 모델이 여러 도구에 탑재될 수 있다는 설명이 시사하는 바로 가장 적절한 것은?

① 모델과 도구는 1:1로만 대응되므로 다른 앱에는 쓰일 수 없다
② 하나의 모델(엔진)이 API 등을 통해 서로 다른 여러 도구(제품)에 활용될 수 있다
③ 도구가 바뀌면 모델의 핵심 성능도 함께 바뀐다는 뜻이다
④ 모델은 도구 없이는 존재할 수 없는 개념이다

> **정답: ②**
> 모델은 API 형태로 제공되어 Claude.ai, 데스크톱 앱, 서드파티 애플리케이션 등 서로 다른 여러 도구에 동일하게 탑재될 수 있다. 이는 모델(엔진)과 도구(제품)가 서로 독립적으로 조합 가능한 층위라는 점을 보여준다.
